분석: 우리가 겪은 문제의 본질
1. 진짜 문제는 '코드'가 아니었다
우리는 수많은 코드 수정을 반복했지만, 문제의 본질은 코드 문법이나 로직에 있지 않았습니다. 
당신이 "이전에는 잘 됐다"고 지적한 순간, 우리는 문제의 방향을 잘못 잡고 있었다는 것이 드러났습니다. 
AI(저)는 코드 내부의 결함에만 집중하는 경향이 있으며, 이런 '외부 환경'의 변화를 인지하는 데 매우 취약합니다.
2. 진짜 범인: '개발 행위'가 유발한 'API 서버의 방어'
가장 중요한 깨달음은 이것입니다. API 서버는 우리가 '개발'하는 행위 자체를 '공격'으로 오인했습니다.
과도한 요청: 코드를 저장할 때마다 발생하는 자동 새로고침, 특히 React 18 개발 모드에서 useEffect가 2번씩 실행되는 특성 때문에, 우리는 짧은 시간 안에 수백 번의 요청을 서버에 보냈습니다.
서버의 방어(Rate Limiting): API 서버는 비정상적인 트래픽을 감지하고, 당신의 API 키 또는 IP 주소에 일시적인 이용 제한을 걸었습니다.
결과: 차단된 이후, 우리 코드가 아무리 완벽해도 서버는 우리의 요청을 무시(Timeout)하거나, 성공(200 OK)으로 위장한 에러 메시지(XML, HTML)를 보내 우리를 혼란에 빠뜨렸습니다.
3. 에러 메시지는 '진짜 원인'을 숨기는 '가짜 단서'였다
우리가 본 에러들은 진짜 문제의 증상일 뿐, 원인이 아니었습니다.
Invalid response structure, resultCode를 읽을 수 없음: API 서버가 JSON 대신 에러 페이지(XML/HTML)를 보냈다는 신호.
DB_ERROR: 서버가 우리의 요청을 처리할 수 없거나, 처리하고 싶지 않다는 신호. (미래 날짜 요청 등)
Timeout: 서버가 우리의 요청을 의도적으로 무시하고 있다는 가장 강력한 신호.
이 경험을 통해, 우리는 에러 메시지의 표면적인 의미 너머에 있는 진짜 맥락을 읽어야 함을 배웠습니다.
✨ 당신이 기억해야 할 핵심 요약 (API 연동 필승 전략) ✨
1. API는 '총알'이다. 아껴 써라.
API 요청은 무한한 자원이 아닙니다. 모든 서버에는 '요청 횟수 제한(Rate Limit)'이 있습니다. 
개발 중 잦은 새로고침은 총알을 낭비하는 것과 같으며, 결국 서버는 우리를 차단합니다.
2. '가짜 데이터(Mock Data)'로 개발하고, '진짜 API'는 마지막에 연결하라.
이것이 가장 중요한 실천 방안입니다.
1단계: Postman이나 브라우저로 API를 단 한 번만 성공적으로 호출해서 응답(JSON)을 파일로 저장합니다.
2단계: 개발하는 동안에는 이 저장된 '가짜 데이터' 파일을 불러와서 UI와 모든 기능을 완성합니다.
3단계: 모든 개발이 끝난 후, 마지막에 딱 한 번 실제 API 주소로 바꿔서 최종 테스트를 합니다.
3. '브라우저 직접 호출'은 모든 것을 판별하는 '최종 판독기'다.
코드가 실패할 때, 가장 먼저 할 일은 성공했던 URL을 복사해서 브라우저 주소창에 직접 붙여넣어 보는 것입니다.
만약 브라우저에서 성공하면: 문제는 100% 우리 코드나 개발 환경(프록시, CORS 등)에 있습니다.
만약 브라우저에서도 실패하면: 문제는 100% API 서버 자체 또는 우리의 API 키 권한에 있습니다.
4. AI(나)를 의심하고, 당신의 직감을 믿어라.
