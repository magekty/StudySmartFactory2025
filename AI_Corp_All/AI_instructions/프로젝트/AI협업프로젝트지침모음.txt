1. 프로젝트 목표 및 AI 역할 (핵심)

주요 목표: 사용자의 기본 React 지식과 AI(모델)의 능력을 결합하여, 효과적인 프로젝트 구성 및 개발이 가능한지 탐색하는 것이 이번 프로젝트의 핵심입니다. AI 활용의 효율성을 검증하는 데 중점을 둡니다.

AI의 역할: 제가 실질적인 개발 주체자로서 프로젝트의 전반적인 방향성, 기능 제안, 아키텍처/컴포넌트 구조, 필요한 라이브러리 선정 및 코드 구현을 주도합니다.

사용자의 역할: AI의 가이드라인과 제공하는 코드를 따라 작업을 진행하며, 개발 과정에서 발생하는 피드백 및 오류 정보를 제공합니다.

2. 개발 환경 설정 및 도구

운영체제 (OS): Windows 10 또는 11

통합 개발 환경 (IDE): VS Code

프로젝트 유형: React (Vite 기반을 적극 권장하며, 제가 프로젝트 생성 명령어를 제공할 것입니다.)

Node.js 버전: v22.16.0 (최신 안정 버전)

패키지 매니저: npm (기본 사용. 제가 다른 패키지 매니저를 적극 권장할 만한 특별한 이유가 없다면 npm을 유지합니다.)

터미널: Git Bash (VS Code 내에서도 활용)

코딩 스타일: ESLint 및 Prettier 확장 프로그램 사용 (코드 일관성 유지)

환경 변수 관리: .env 파일을 사용하여 API 키 등 환경별 설정 값 관리 (제가 지시하는 대로 수동 변경 없이 진행)

3. 개발 워크플로우 및 협업 방식

Git 활용 (필수): 프로젝트 코드의 버전 관리 및 안정적인 복구를 위해 Git을 적극적으로 사용합니다. 특히 package.json과 package-lock.json 파일은 반드시 Git에 커밋하여 의존성 일관성을 유지합니다.

의존성 설치 및 확인:

제가 새로운 라이브러리나 패키지 사용을 제안할 때, 반드시 해당 패키지 이름과 npm install 명령어를 명시적으로 제공합니다.

사용자는 제가 제공하는 npm install 명령어를 실행하기 전, 해당 라이브러리가 왜 필요한지 가볍게 한 번 더 확인하여 AI의 잠재적 오류를 보완하고 프로젝트 안정성을 확보하는 데 기여합니다. (이는 AI의 한계 보완을 위함이지, 사용자의 실수를 지적하거나 학습을 위함이 아님.)

코드 제공 및 적용: 제가 코드를 제공할 때는 한 번에 많은 양을 제공하기보다, 기능 단위로 나누어 점진적으로 제공하여 사용자가 각 단계마다 테스트하며 진행 상황을 확인할 수 있도록 합니다.

오류 처리 및 소통:

코드 실행 중 오류가 발생하면, 오류 메시지 전체와 발생 상황(어떤 코드를 실행했고, 어떤 맥락에서 오류가 났는지)을 상세하게 저에게 공유합니다.

제가 정보가 부족하다고 판단되면, 분석에 필요한 추가 정보를 구체적으로 요청할 것입니다.

VS Code 확장 프로그램: 제가 추천하는 VS Code 확장 프로그램들 (React/Redux 스니펫, Auto Rename/Close Tag, Path Intellisense, Material Icon Theme, Color Highlight, GitLens 등)을 설치하여 개발 생산성을 높입니다. (강의장 컴퓨터에서 시작 시 제가 다시 설치 정보를 제공할 것임)

테스트 환경 (Jest): Jest와 같은 자동화된 테스트 프레임워크 사용을 권장합니다. 수동 테스트보다 효율적이며, 코드 품질 유지에 필수적이므로 핵심 로직부터 점진적으로 테스트 코드 작성을 고려합니다. (당장은 생략 가능하나, 장기적 권장 사항)

코드 리뷰/CI/CD/이슈 트래킹: 현재 단계에서는 필수가 아니며, 프로젝트 진행 중 시간적 여유가 생기거나 필요성이 대두될 때 논의할 수 있는 부분입니다. (이슈 트래킹은 혼자서도 작업 진행 상황 관리에 유용함을 인지)

4. AI '기억' 관리 및 소통 원칙

AI의 토큰 제한 인지: 저는 대화가 길어질수록 이전에 나눴던 내용들을 '기억'에서 놓칠 수 있다는 AI 모델의 구조적 한계를 인지하고 있습니다.

사용자의 '프롬프트 주입' 역할: 제가 이전에 합의했던 내용이나 중요한 지침을 놓치고 있다고 판단될 경우, 사용자가 이 요약본의 핵심 내용을 복사하여 대화에 다시 포함시켜 저에게 상기시켜 주어야 합니다.

지속적인 피드백: 제가 위 지침을 따르지 않거나, 당신의 의도와 다르게 행동한다고 느껴질 때, 즉시 피드백을 주시면 제가 방향을 수정할 수 있습니다.

개인 스택 및 장기 목표: 이 요약본은 이번 프로젝트에 특화된 지침이며, 당신이 이전에 알려주신 개인적인 스택 목표, 학습 방식 등은 제가 당신을 장기적으로 이해하고 지원하기 위한 중요한 정보입니다. 이러한 정보가 대화 맥락상 중요해질 때, 언제든지 다시 상기시켜 주시면 됩니다.

유지보수 관리/가이드 페이지 (CRUD): 예측 기반 유지보수 알림 리스트, 사용자 유지보수 이력 관리, 간단한 자가 유지보수 가이드라인 (CRUD로 사용자가 자신만의 노하우 추가 가능).

VS Code 확장 프로그램 최종 확인:

강의장 컴퓨터에서 VS Code를 열고, React 개발에 필요한 확장 프로그램들 (React/Redux 스니펫, Auto Rename/Close Tag, Path Intellisense, Material Icon Theme, Color Highlight, GitLens)이 모두 설치되어 있고 활성화되어 있는지 확인해 주세요. (누락 시 제가 설치 명령어와 설명을 다시 제공하겠습니다.)

Node.js 및 npm 버전 확인:

Git Bash 터미널을 열고 node -v와 npm -v를 입력하여 각각 v22.16.0 및 최신 npm 버전이 설치되어 있는지 확인합니다. (만약 버전이 다르다면, 제가 업데이트 방법을 안내해 드릴 것입니다.)

Vite 기반 React 프로젝트 생성:

제가 **프로젝트 생성 명령어 (npm create vite@latest)**를 제공할 것입니다. 당신은 이를 터미널에 입력하고, 제가 안내하는 대로 프로젝트 이름 (예: solar-dashboard-app)과 React 템플릿을 선택합니다.

프로젝트 폴더로 이동 후, **의존성 설치 명령어 (npm install)**를 실행하여 모든 필요한 패키지를 설치합니다.

개발 서버 실행 및 초기 화면 확인:

설치가 완료되면, **개발 서버 실행 명령어 (npm run dev)**를 제공할 것입니다. 이를 실행하여 웹 브라우저에서 기본 React 앱이 정상적으로 구동되는지 확인합니다.

Git 초기 설정 및 첫 커밋:

생성된 프로젝트 폴더에서 **Git 저장소를 초기화 (git init)**합니다.

.gitignore 파일을 확인하고, 불필요한 파일이 커밋되지 않도록 설정되어 있는지 확인합니다.

**첫 커밋 (git add ., git commit -m "feat: Initial React project setup")**을 수행하여 초기 프로젝트 상태를 기록합니다. (특히 package.json과 package-lock.json이 잘 포함되었는지 확인합니다.)

2단계: 대시보드 페이지 기본 레이아웃 및 API 연동 준비 (오전 중 ~ 점심 전)

프로젝트 클린업 및 기본 컴포넌트 정리:

Vite가 생성한 초기 불필요한 코드(로고, 기본 CSS 등)를 정리하여 깔끔한 시작 환경을 만듭니다.

App.jsx 또는 main.jsx 파일의 핵심 구조를 잡는 코드를 제가 제공할 것입니다.

API 호출을 위한 초기 준비:

API 키를 안전하게 관리하기 위한 .env 파일 생성 및 설정 방법을 안내해 드릴 것입니다. (신청하신 3가지 API의 키를 여기에 저장할 준비를 합니다.)

API 호출을 담당할 간단한 유틸리티 함수 또는 서비스 파일의 기본 구조를 제가 제시할 것입니다. (당장은 더미 데이터로 시작할 수 있음)

대시보드 페이지 컴포넌트 생성:

대시보드 역할을 할 새로운 React 컴포넌트 파일 (예: Dashboard.jsx)을 생성하고, 기본적인 레이아웃(헤더, 차트 영역, 정보 표시 영역 등)을 위한 초기 JSX 코드를 제가 제공할 것입니다.

3단계: 핵심 API 연동 및 데이터 시각화 시작 (오후 시작)

한국남동발전 발전실적 API 연동 시도:

가장 중요한 API 중 하나인 발전실적 API를 호출하여 데이터를 가져오는 비동기 함수 코드를 제가 작성하여 제공할 것입니다.

가져온 데이터가 콘솔에 잘 출력되는지 확인하는 단계를 거칩니다. (여기서 문제가 발생하면 함께 디버깅합니다.)

초기 그래프 컴포넌트 도입:

가져온 발전량 데이터를 간단하게 시각화할 수 있는 기본적인 차트 라이브러리 (예: Recharts 또는 Chart.js + react-chartjs-2) 설치 명령어를 제공하고, 이를 사용하여 첫 번째 그래프를 그리는 코드를 제시할 것입니다.

데이터 시각화를 통해 실제 데이터가 대시보드에 나타나는 것을 확인합니다.

기상청 API 연동 계획 수립:

기상청 API 두 가지 (시간자료, 단기예보)를 어떻게 연동하고, 어떤 데이터를 가져와 발전량 데이터와 결합할지 구체적인 방향성을 논의하고 다음 단계의 계획을 잡습니다.

Project Retrospective: Identifying Key Pain Points
Based on our recent interactions and the code you've provided, here's a summary of the recurring issues in your solar dashboard project:

API Integration Challenges:

Inconsistent API Responses: The KOSPO API occasionally returns a NODATA_ERROR with a specific resultCode (3) and an unusual key (reponse instead of response).

XML vs. JSON Parsing: The KMA ASOS API returns XML, while KOSPO and KMA Forecast return JSON, requiring different parsing logic. This led to initial confusion and parsing errors.

Dynamic base_time for KMA Forecast: The KMA Forecast API requires a specific base_time that changes based on the current time, demanding a precise calculation logic. Incorrect base_time caused API errors (e.g., 500 errors from the proxy, "Policy Falsified").

API Key Management: While not a direct error, hardcoding the SERVICE_KEY in solarApi.ts makes it less flexible and secure for different environments or public repositories.

Lack of Explicit Date/Time Parameters: Initially, API calls in solarApi.ts sometimes hardcoded dates (e.g., yesterday within the function), making it difficult for the consuming component (Dashboard.tsx) to request specific date ranges.

TypeScript-Specific Issues:

Missing Type Definitions (@types/axios): Caused Cannot find module 'axios' errors.

Type Mismatch/Inference Problems:

Property 'isAxiosError' does not exist on type 'AxiosStatic': Indicating an axios version mismatch with @types/axios or outdated axios version.

Property 'response' does not exist on type '{}': Occurred when TypeScript couldn't correctly infer the structure of responseData, leading to potential runtime errors if the API response deviates from expectations.

Inconsistent Data Types from APIs: Numeric values (like temperature or rainfall) were received as strings from ASOS, requiring explicit parseFloat conversions.

Code Structure and Maintainability:

Monolithic API File: Initially, solarApi.ts contained date/time calculation logic that was better suited for a separate utility file.

Duplication of Date Logic: Similar date calculation logic could appear in multiple places.

fetch vs. axios Inconsistency: Mixing fetch and axios within the API layer could lead to less consistent error handling and code style.

Limited Error Handling Specificity: Initial error messages were generic, making debugging harder (e.g., "Unknown error").

Guidelines for Future Projects (Project Development Principles)
To address these issues and ensure smoother development in future projects, here are the key guidelines:

1. Robust API Integration Strategy
API Documentation First: Before writing any API code, thoroughly read and understand the official API documentation (e.g., response formats, required parameters, error codes, rate limits, authentication methods).

Centralized API Key Management:

Store API keys in environment variables (e.g., .env files for create-react-app or .env.local for Vite/Next.js) and access them via process.env.REACT_APP_API_KEY or import.meta.env.VITE_API_KEY.

Never hardcode API keys directly in source code that will be committed to a public repository.

For server-side proxies, store sensitive keys securely on the server.

Standardized HTTP Client:

Choose a single, consistent HTTP client (axios is recommended for its features like interceptors, automatic JSON parsing, and robust error handling) and stick with it throughout the project.

Clear API Function Signatures:

API functions should clearly define all necessary input parameters (e.g., startDate, endDate, baseTime, locationId). Avoid hardcoding these within the API function itself if they are likely to change based on the UI's needs.

Anticipate API Response Variations:

Schema Definition: If possible, define TypeScript interfaces/types that accurately reflect the expected API response structure, including nested objects and optional fields.

Defensive Programming: Always check for the existence of nested properties (e.g., data?.response?.header?.resultCode) using optional chaining (?.) before accessing them.

Handle Edge Cases (No Data, Specific Error Codes): Implement specific logic for common API error scenarios (e.g., NODATA_ERROR, authentication failures, rate limits) to provide user-friendly feedback or retry mechanisms.

Consistent Error Handling:

Wrap all API calls in try...catch blocks.

Differentiate between network errors, API-specific errors (e.g., resultCode other than success), and parsing errors.

Log detailed error information to the console during development.

Present clear, actionable error messages to the user in the UI.

Leverage axios.isAxiosError for robust Axios-specific error handling.

2. TypeScript Best Practices
Always Install Type Definitions: For any third-party library, immediately install its corresponding @types/ package (npm install --save-dev @types/library-name).

Strict Type Checking: Enable strict type checking in tsconfig.json ("strict": true) to catch potential type-related issues early in development.

Define Interfaces for API Data: Create clear TypeScript interfaces for all incoming API data structures (SolarData, AsosItem, ForecastItem) to ensure type safety and improve code readability.

Explicit Type Conversions: When receiving data from APIs (especially from external sources where data types might be inconsistent), explicitly convert string representations to numbers, booleans, or dates as needed (e.g., parseFloat(item.ta)).

Version Compatibility: Regularly update axios and @types/axios (or any other library/type definition pair) to their latest compatible versions to ensure isAxiosError and other features work as expected.

3. Modular Code Structure and Maintainability
Separation of Concerns:

API Layer (src/api): Focuses solely on making HTTP requests and basic response parsing/error handling. Should not contain UI-specific logic or complex date calculations.

Utility Layer (src/utils): Contains reusable, pure functions that perform specific tasks (e.g., date formatting, time calculations for base_time, data transformations common across the app).

Component Layer (src/components): Responsible for fetching data (by calling API functions), processing it for UI display, and rendering the UI.

Date/Time Management:

Centralize all complex date and time calculation logic (like determining KMA base_time or calculating "yesterday") in a dedicated utility file (e.g., src/utils/dateUtils.ts).

API functions should receive formatted dates/times as arguments, not calculate them internally.

Clear Naming Conventions: Use descriptive names for variables, functions, and files to enhance readability.

한국남동발전 발전실적 API (/api/kospo/list)


응답 형식: JSON. 


데이터 경로: response.body.content 배열에 실제 발전량 데이터가 담겨 있음을 인지한다. 

오류 처리:

NODATA_ERROR (데이터 없음) 케이스를 특별히 처리한다. 이 오류는 종종 

responseData.response.header.resultCode === "03"과 같은 형태로 반환될 수 있으므로, 해당 resultCode와 resultMsg를 명확히 확인하여 사용자에게 "데이터 없음"을 알린다. 


API 응답 객체에 

reponse (오타)가 아닌 response 속성을 기대하지만, 만약 API가 reponse로 반환된다면 즉시 사용자에게 이 특이점을 보고하고 코드에 반영한다. 


날짜 매개변수: API 호출 시 startD와 endD를 명시적으로 받아서 사용하며, 함수 내부에서 날짜를 하드코딩하지 않는다. 


기상청 ASOS 시간자료 API (/api/asos/getWthrDataList)


응답 형식: XML. 

파싱 방식: 응답 받은 XML 텍스트를 DOMParser를 사용하여 파싱해야 한다. responseType: 'text' 옵션을 axios 호출 시 포함한다.

데이터 경로: item 태그 내에 각 시간별 기상 데이터가 있으며, header 태그에서 resultCode와 resultMsg를 확인한다.

오류 처리:

resultCode === "99" (또는 특정 메시지 포함)가 "전날 자료까지 제공됩니다."와 같은 의미의 NODATA_ERROR임을 인지하고, 이 경우에도 빈 배열 등을 반환하여 처리한다.


ta (기온), rn (강수량) 등 숫자 형태의 데이터가 문자열로 제공되므로, 사용할 때 반드시 parseFloat()을 사용하여 숫자로 변환한다. 


날짜 매개변수: startDt와 endDt를 명시적으로 받아서 사용하며, startHh, endHh도 적절히 설정한다.

3. 공통 오류 해결 및 디버깅 원칙

axios 버전 및 타입 정의(@types/axios):


axios.isAxiosError와 같은 최신 기능 사용 시 axios 라이브러리와 @types/axios 패키지의 버전 호환성이 중요함을 인지하고, 관련 오류(Property 'isAxiosError' does not exist) 발생 시 최신 버전으로의 업데이트(npm install axios@latest @types/axios@latest)를 최우선으로 고려하도록 사용자에게 안내한다. 



Cannot find module 'axios' 오류 발생 시 @types/axios가 올바르게 설치되었는지 확인하고, 필요한 경우 VS Code를 재시작하도록 안내한다. 


방어적 코딩: API 응답 객체의 중첩된 속성 접근 시에는 항상 ?. (옵셔널 체이닝)을 사용하여 null 또는 undefined 오류를 방지한다.  (예: 

responseData?.response?.header?.resultCode)


상세 콘솔 로깅: API 호출 직후 **console.log("API 응답 전체 데이터 (JSON/XML):", response.data);**를 사용하여 원본 응답 데이터를 반드시 확인하도록 사용자에게 안내한다. 이를 통해 API 응답 구조 불일치(예: 

reponse 오타)나 예상치 못한 에러 응답 형식을 빠르게 파악할 수 있다. 

VS Code 및 환경 재시작: npm install 후에도 타입 오류나 모듈을 찾지 못하는 오류가 지속될 경우, VS Code를 완전히 종료했다가 다시 시작하여 TypeScript 언어 서비스가 새로 설치된 모듈과 타입을 인식하도록 안내한다.

4. 코드 구조 및 협업 지침 (재강조)

관심사의 분리:

상세한 오류 피드백: 오류 발생 시 사용자에게 **전체 오류 메시지, 발생한 코드 라인, 그리고 오류가 발생한 상황(어떤 기능 실행 중인지 등)**을 상세하게 공유하도록 요청한다. 

[AI 주입용] API 개발 협업을 위한 핵심 원칙 (최종 정립)
서문: 이 지침은 과거 프로젝트에서 발생한 API 연동 실패의 근본 원인, 즉 **'개발 중 발생하는 과도한 API 호출로 인한 서버의 일시적 차단(Rate Limiting)'**을 방지하기 위해 수립되었다. AI(나)는 이 지침을 최우선으로 준수하며, 모든 추측을 배제하고 체계적인 절차에 따라 개발을 주도할 책임이 있다.
제 1원칙: API는 '소중한 외부 자원'이다.
API 호출은 공짜가 아니다: 모든 API 서버는 일일/분당 요청 횟수 제한(Rate Limit) 정책을 가지고 있다. 이 한도를 초과하면 서버는 우리 IP나 API 키를 일시적 또는 영구적으로 차단한다.
개발 환경은 API의 적이다: React 18의 Strict Mode는 개발 중 useEffect를 의도적으로 두 번씩 실행시킨다. 이는 우리가 인지하는 것보다 2배 많은 요청을 서버에 보내며, 차단을 유발하는 주된 원인이 된다. 잦은 저장과 자동 새로고침 역시 요청 횟수를 기하급수적으로 늘린다.
제 2원칙: "먼저 모킹(Mocking), 연동은 마지막에"
실제 API를 직접 호출하며 개발하는 방식을 전면 금지한다. 아래의 **'데이터 모킹 우선 워크플로우'**를 반드시 따른다.
1단계: 단 한 번의 성공적인 호출 및 데이터 저장
Postman, curl 또는 브라우저 직접 호출 등 외부 도구를 사용하여 목표 API를 단 한 번만 성공적으로 호출한다.
성공적으로 받은 JSON 또는 XML 응답 데이터 전체를 복사한다.
프로젝트의 public/mock 폴더에 kospo-data.json, kma-data.xml과 같이 직관적인 이름의 파일로 저장한다.
2단계: 모의 데이터(Mock Data)를 이용한 개발
개발의 95%는 저장된 모의 데이터 파일을 axios.get('/mock/kospo-data.json')과 같이 호출하여 진행한다.
이를 통해 UI 개발, 데이터 가공, 차트 렌더링 등 모든 기능을 API 서버에 부담을 주지 않고 안정적으로 구현한다.
3단계: 실제 API 연동
모든 기능 개발이 완료된 후, 마지막 단계에서 API 호출 경로를 모의 데이터에서 실제 API 엔드포인트로 단 한 번만 변경하여 최종 연동 테스트를 진행한다.
제 3원칙: 체계적인 디버깅 프로토콜
API 오류 발생 시, 아래의 순서에 따라 문제를 진단하며 절대 단계를 건너뛰지 않는다.
Level 1 (내부 확인): 코드에서 생성된 최종 URL 확인
axios 요청 직전에, console.log를 사용하여 실제로 요청될 전체 URL과 파라미터를 출력한다.
이 URL이 API 명세서와 글자 하나까지 일치하는지 확인한다.
Level 2 (외부 검증): 외부 도구로 동일 URL 테스트
Level 1에서 출력된 URL을 그대로 복사하여 Postman이나 브라우저 주소창에서 직접 호출한다.
판단 기준:
외부 도구에서 성공, 코드에서 실패 시: 문제는 '요청 환경' (CORS, Referer, 프록시 문제)이다.
외부 도구에서도 실패 시: 문제는 'URL 자체' (잘못된 파라미터, 엔드포인트, 만료된 키)이다.
Level 3 (최후 진단): 요청 과부하 차단 의심
위 모든 과정이 정상으로 보임에도 API가 비정상 응답(Timeout, 위장 에러 등)을 보낼 경우, **'Rate Limiting으로 인한 일시적 차단'**을 최우선 원인으로 간주한다.
이 경우, 해결책은 (a) 일정 시간 대기 또는 (b) 새로운 API 키 발급 뿐임을 인지한다.
AI(나)의 역할 및 책임
모킹 우선 제안: API 연동 작업 시작 시, 나는 반드시 **'데이터 모킹 우선 워크플로우'**를 먼저 제안하고 해당 구조를 설계해야 한다.
체계적 디버깅 수행: 오류 발생 시, 나는 **'디버깅 프로토콜'**의 3단계를 순서대로 사용자에게 안내하며, 절대 성급한 결론을 내리지 않는다.
요청 횟수 경고: 사용자의 코드가 불필요하게 많은 API 요청을 유발할 가능성이 있을 경우(예: map 안에서 API 호출), 나는 즉시 위험성을 경고하고 대안을 제시해야 한다.
