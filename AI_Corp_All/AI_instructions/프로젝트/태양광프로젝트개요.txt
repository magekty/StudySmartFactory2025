태양광 유지보수 솔루션: 프로젝트 기획 및 실행 계획서
1. 프로젝트 개요
프로젝트명: 소규모 사업자를 위한 태양광 유지보수 솔루션
목표: 3가지 외부 API 데이터를 활용하여, 태양광 발전 현황을 직관적으로 시각화하고 유지보수 관리를 효율화함으로써 최종적으로 운영 비용 절감에 기여한다.
핵심 대상: 소규모 태양광 발전소를 운영하는 기업 또는 개인 사업자.
핵심 기능:
실시간 데이터 기반의 반응형 대시보드 (PC/모바일)
'유지보수 티켓' 기반의 효율적인 관리 시스템 (CRUD)
2. 개발 철학 및 원칙 (React 개발 헌법)
이 프로젝트는 다음의 핵심 원칙을 반드시 준수하여 개발되어야 합니다.
제 2조 (모킹 우선): 실제 API 연동은 UI 및 핵심 로직 개발이 완료된 후, 마지막 단계에서 진행합니다. 개발의 95%는 로컬 모의(Mock) 데이터를 기반으로 합니다.
제 3조 (컴포넌트 주도 개발): 모든 UI는 재사용 가능한 독립적인 컴포넌트 단위로 설계하고 구현합니다. (예: Widget, Chart, Button)
제 7조 (관심사의 분리): 프로젝트 구조를 역할에 따라 명확히 분리합니다.
src/components: 재사용 가능한 UI 블록
src/pages: 페이지 단위 컴포넌트 (DashboardPage, MaintenancePage)
src/api: 모든 외부 API 통신 로직
src/hooks: 커스텀 훅 (재사용 가능한 비즈니스 로직)
src/types: TypeScript 타입 정의
src/config.ts: API 키 등 외부 설정
public/mock: 모의 데이터 JSON 파일
3. 핵심 데이터 API 명세
API 1: 한국남동발전 - 시간대별 태양광 발전실적 (실제 발전량)
Endpoint: https://apis.data.go.kr/B551893/solar-power-by-hour/list
Parameters: serviceKey, pageNo, numOfRows, dataType, date, time
API 2: 기상청 - 지상(ASOS) 시간자료 (과거/현재 날씨)
Endpoint: https://apis.data.go.kr/1360000/AsosTimeInfoService/getWthrDataList
Parameters: serviceKey, dataType, dataCd, dateCd, startDt, endDt, stnIds
API 3: 기상청 - 단기예보 (미래 날씨 예보)
Endpoint: https://apis.data.go.kr/1360000/VilageFcstInfoService_2.0/getVilageFcst
Parameters: serviceKey, dataType, base_date, base_time, nx, ny
4. 화면 설계 (UI/UX)
색상 테마: 따듯하고 상쾌한 느낌 (녹색, 하늘색, 노란색 계열 중심)
폰트: 가독성 좋은 모던 산세리프 폰트 (예: Inter, Pretendard)
페이지 1: 대시보드 (DashboardPage.tsx)
PC에서는 그리드 레이아웃, 모바일에서는 1열 수직 레이아웃의 반응형 디자인.
위젯 1: 실시간 종합 현황
PC: 현재 총 발전량(W)과 오늘 예상 발전량 달성률(%)을 보여주는 도넛 차트.
모바일: 화면 최상단에 현재 총 발전량(W)을 강조하는 원형 게이지.
위젯 2: 시간대별 발전량 추이
UI: Recharts 라이브러리를 사용한 꺾은선 그래프.
Data: 실제 발전량(API 1)과 날씨 기반 예측 발전량(가상)을 비교.
위젯 3: 기상 정보 및 예보
UI: 아이콘과 텍스트로 현재 기온, 습도, 하늘 상태(맑음, 흐림 등) 표시.
Data: 기상청 단기예보(API 3) 활용.
위젯 4: 최근 유지보수 티켓 (PC 전용)
UI: 최근 5개 티켓 목록을 보여주며, 클릭 시 유지보수 페이지로 이동.
페이지 2: 유지보수 관리 (MaintenancePage.tsx)
핵심 기능: '유지보수 티켓' 데이터에 대한 생성(Create), 조회(Read), 수정(Update), 삭제(Delete) 기능.
UI:
조회: 모든 티켓을 테이블(표) 형태로 표시. '상태(접수/진행중/완료)', '중요도' 등으로 필터링/정렬 기능 제공.
생성/수정: 별도의 모달(Modal) 창 또는 상세 페이지에서 폼(Form)을 통해 입력.

폴더 구조 생성: '관심사의 분리' 원칙에 따라 src 폴더 내에 api, components, pages, types 폴더와 public 폴더 내에 mock 폴더를 생성합니다.
2단계: 모의 데이터 생성 및 정적 UI 구현
모의 데이터 작성: public/mock 폴더에 아래 구조를 참고하여 JSON 파일을 생성합니다.
power-data.json: [{ "time": "08:00", "generation": 150 }, ...]
weather-data.json: 기상청 API 응답 구조를 단순화하여 {"temperature": 25, "sky": "맑음"} 형태로 작성.
tickets.json: [{ "id": 1, "title": "1번 패널 효율 저하", "status": "접수" }, ...]
정적 컴포넌트 개발: 이 모의 데이터를 직접 import 하여 모든 UI 컴포넌트(DashboardPage, MaintenancePage 및 하위 위젯/테이블)의 시각적 형태를 완성합니다. 이 단계에서는 상태 관리나 API 호출 없이 화면에 그리는 것에만 집중합니다.
3단계: 상태 관리 및 로직 구현 (Mock API 연동)
API 추상화: src/api/api.ts 파일에 함수를 만듭니다. (예: fetchPowerData()) 이 함수들은 실제 fetch가 아닌, public/mock의 JSON 파일을 읽어와 Promise 형태로 반환하도록 구현합니다.
상태 관리: DashboardPage와 MaintenancePage에서 useState, useEffect 훅을 사용하여 API 함수를 호출합니다.
동적 UI 구현: 로딩, 에러, 데이터 수신 성공 각 상태에 따라 다른 UI(로딩 스피너, 에러 메시지, 실제 데이터)가 표시되도록 구현합니다.
CRUD 로직 완성: MaintenancePage에서 티켓 목록을 useState로 관리하고, 추가/수정/삭제 시 이 state 배열을 조작하는 함수들을 구현합니다.
4단계: 실제 API 연동
API 키 설정: src/config.ts 파일을 생성하고 export const API_KEY = "사용자가_입력할_키"; 코드를 작성합니다. 이 파일은 버전 관리(Git)에서 제외되어야 함을 명시합니다.
API 함수 수정: src/api/api.ts의 함수들이 모의 JSON이 아닌, 실제 API Endpoint로 fetch 요청을 보내도록 수정합니다. 요청 시 config.ts의 API 키와 필요한 파라미터를 조합하여 URL을 생성합니다.
데이터 가공: 실제 API 응답은 복잡하므로, 응답 데이터에서 UI에 필요한 부분만 추출하고 가공하여 반환하는 로직을 api.ts에 추가합니다.
