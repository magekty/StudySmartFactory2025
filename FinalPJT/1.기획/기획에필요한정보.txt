## 📌 1. 프로젝트 개요

**목표:** 설비 제어 → IoT 수집 → API 백엔드 → 운영 UI → DB → 데이터 분석까지 전 과정이 연계되는 **스마트팩토리 통합 MES 시스템** 구축.

**기술 스택:**

- 설비 제어 및 IoT: `C#`
- 백엔드 API 및 관리 시스템: `Java (Spring Boot)`
- 운영 UI 및 관리자 대시보드: `React`
- 데이터 저장 및 분석: `MySQL`, `Power BI`

---

## ✅ 2. 공통 개발 지침

### 2.1 네이밍 규칙

- **camelCase**: Java, C#, JS에서 변수/메서드 등
- **snake_case**: DB 컬럼 및 테이블
- **Kebab-case**: URL Path(`/api/order-items`)
- 상수명: 대문자+언더바 (`MAX_LENGTH`)

### 2.2 주석 및 문서화

- 모든 함수 및 클래스에는 **의미 있는 주석** 작성(120자 이내)

### 2.3 Git 협업 전략

- 브랜치 전략: `main`, `develop`, `feature/{기능명}`
- 커밋 메시지: `타입: 변경내용`
    - 예: `feat: 생산 지시 등록 기능 추가`

타입 예시:

- feat: 기능 추가
- fix: 버그 수정
- docs: 문서 변경
- refactor: 리팩토링

### 2.4 공통 에러 응답 형식(JSON)

```json
{
  "status": 400,
  "message": "잘못된 요청입니다.",
  "errorCode": "INVALID_INPUT",
  "timestamp": "2025-07-23T09:00:00+09:00"
}

```

## 🧩 3. 백엔드(Spring Boot) 개발 가이드

### 3.1 REST API 설계

- URI는 **리소스 중심으로** 작성 (동사 ❌)
- 복수형 리소스 명 사용
- 하위 리소스 표현: `/orders/{orderId}/steps`

| 메서드 | 용도 | 예시 |
| --- | --- | --- |
| GET | 조회 | `/machines/1` |
| POST | 생성 | `/orders` |
| PUT | 전체 수정 | `/orders/1` |
| PATCH | 부분 수정 | `/orders/1/status` |
| DELETE | 삭제 | `/orders/1` |

### 3.2 DTO / Entity 분리

- Entity는 DB와 직접 매핑
- DTO는 요청(Request), 응답(Response)에 따라 세분화

### 3.3 JPA 및 테이블 설계

- 기본키는 `id` (숫자), 의미 있는 경우 `code` (문자)
- 모든 테이블에 `pk` 반드시 지정
- 컬럼명은 snake_case

매핑 시 주의:

```java
@Column(name = "user_id")
private Long userId;

```

## 🛠 5. C# (IoT 수집 및 설비 제어) 개발 가이드

### 5.1 기본 구조

- 설비 모듈 별로 클래스 분리
- 시리얼, Modbus, OPC-UA 통신 지원
- 주기적 수집 로직은 Timer 또는 Task 기반 비동기 처리

### 5.2 예외처리 및 로깅

- 모든 통신 오류는 try-catch 처리 후 로그 파일 남김
- NLog 또는 Serilog 등 로깅 프레임워크 활용 가능

### 5.3 CSV/로그 저장

- 로컬 저장 시 날짜별 디렉토리 구성
- CSV 저장 시 헤더 포함, UTF-8 인코딩 고정

## 🧾 6. DB 설계 및 Power BI 연동

### 6.1 테이블 설계 원칙

- 정규화 우선 (1NF~3NF)
- 코드성 테이블 따로 관리 (ex. 설비 상태, 작업 유형)
- 타임스탬프는 반드시 `created_at`, `updated_at` 사용

### 6.2 Power BI 연동

- MySQL ODBC 또는 Direct Query 방식
- 보고서 필터 조건: 기간별, 설비별, 작업자별 등
- KPI 시각화: 생산량, 불량률, 설비 가동률 등

## 🧩 7. 국제 표준 기반 MES 모델 참고

### 7.1 ISA-95 모델 구조

- Level 0: 실제 물리적 설비
- Level 1: 센서/액추에이터 (제어)
- Level 2: PLC, SCADA 등 제어 시스템
- **Level 3: MES (생산운영관리)**
- Level 4: ERP (경영계획)

### 7.2 MESA-11 핵심 기능 (MES의 11가지 기능 영역)

- 상세
    
    
    | 번호 | 기능 영역 | 설명 |
    | --- | --- | --- |
    | 1 | **자원 할당 및 상태 관리** | 인력, 장비, 도구, 자재 등 제조 자원의 사용 가능 여부와 상태를 실시간으로 관리합니다. 예: 설비 점검 상태, 작업자 할당. |
    | 2 | **운영 계획 상세화** | ERP로부터 전달받은 작업 지시를 실행 가능 수준으로 분해하거나 일정에 따라 스케줄링합니다. |
    | 3 | **운영/작업 흐름 관리 (워크플로우)** | 생산 공정의 순서를 관리하고 자동화하며, 공정 변경 요청 및 승인 프로세스를 지원합니다. |
    | 4 | **문서 관리** | 작업 지시서, 설계 도면, 품질 매뉴얼 등 제조 관련 문서를 저장·배포·버전 관리합니다. |
    | 5 | **디스패치 작업 지시** | 현장의 작업자 또는 설비에 작업 지시를 전송하고 수행 상태를 모니터링합니다. |
    | 6 | **제품 추적 및 이력 관리 (Traceability)** | 원자재부터 완제품까지의 모든 이력을 추적하여 품질 문제 발생 시 신속한 원인 분석 및 대응이 가능하게 합니다. |
    | 7 | **공정 데이터 수집 (Data Collection)** | 생산 설비, 센서, IoT 장비로부터 실시간 데이터를 수집하고 저장합니다. 예: 온도, 압력, 작업 시작/완료 시간 등. |
    | 8 | **노동력 관리** | 작업자의 근무 이력, 기술 숙련도, 출결 관리, 자격 등을 관리합니다. |
    | 9 | **품질 관리 (Quality Management)** | 검사 결과 기록, 품질 이상 알림, 통계적 품질 관리(SPC) 기능 등을 통해 제품 품질을 관리합니다. |
    | 10 | **공정 관리 (Process Management)** | 생산 공정의 기준 조건과 실제 작업 조건을 비교해 불일치를 탐지하거나 자동으로 보정합니다. |
    | 11 | **성능 분석 (Performance Analysis)** | OEE, 생산성, 가동률, 불량률 등 KPI를 분석하고 개선을 위한 리포트를 제공합니다. |
1. 자원관리

    ## 3. 🧱 백엔드(Spring Boot) 개발 지침
    
    ### 3.1. 📌 프로젝트 구조 및 계층화 설계
    
    ```bash
    bash
    복사편집
    src
    ├── controller       # API 진입점, DTO 사용
    ├── service          # 비즈니스 로직
    ├── repository       # DB 연동 (JPA)
    ├── domain           # 엔티티 클래스 (JPA 기반)
    ├── dto              # 요청/응답 객체
    ├── config           # 설정 파일 (보안, DB, Swagger 등)
    └── exception        # 예외 처리 전담
    
    ```
    
    > 🌟 초급자는 DTO와 Entity의 차이, Controller와 Service 분리 목적을 명확히 익히는 것이 중요합니다.

    ### 3.2. ✅ 코드 작성 규칙
    
    | 항목 | 규칙 |

    - 클래스명, 인터페이스: PascalCase (`SensorReader`)

    **[React – 운영 UI 및 관리자 대시보드]**
    
    - 파일명: PascalCase (`UserDashboard.jsx`)

    - Props: camelCase (`machineStatus`)

    ## 6. 보안 및 인증/인가 정책
    
    ### 6.1 API 인증 방식
    
    - **JWT 토큰 기반 인증 사용**
        - 발급 위치: 로그인 성공 시
        - 저장 위치: 프론트는 `localStorage` 또는 `HttpOnly Cookie` 선택
        - 유효 기간 관리 + Refresh Token 고려
        - 서버는 `Authorization: Bearer <token>` 헤더로 처리
    - **역할 기반 권한 (RBAC)**
        - 관리자는 모든 권한
        - 일반 작업자: 데이터 조회/입력 제한
        - Spring Security 또는 JWT 클레임 기반으로 처리
    
    ### 6.2 입력값 검증 및 방어
    
    - SQL Injection 방지: ORM 활용 + Prepared Statement
    - XSS 방지: 클라이언트 단 escape 처리
    - 파일 업로드 시 확장자/사이즈 체크
    - REST API에서는 DTO로 전달받고 검증 (`@Valid`, `@Pattern`, `@Size` 등)

    | 기능 정상 동작 | 입력값에 따라 올바른 결과가 반환되는가 | 정상 주문 요청 시 DB에 저장 및 응답 코드 `200` |
    | 예외 처리 | 잘못된 입력값 또는 예외 상황 시 처리 | 수량이 0일 때 오류 메시지 반환 및 `400` |
    | DB 반영 확인 | 로직 실행 후 DB 반영 여부 | 설비 상태 변경 시 `machine_status` 테이블 반영 여부 |
    | 필수 필드 검증 | 누락된 필드 입력 시 오류 처리 | `order_id` 누락 시 "필수값 누락" 메시지 |
    | 응답 구조 검증 | API 응답 포맷 일관성 | `code`, `message`, `data` JSON 구조 유지 |
    | 보안 테스트 | 인증/인가 여부 확인 | 토큰 없으면 접근 불가, 역할 없는 유저는 차단 |
    | 경계 조건 테스트 | 최대 길이, 음수 값 등 경계값 처리 | `quantity` = -1 일 때 에러 반환 |
    | 성능(선택적) | 대량 데이터에 대한 처리 성능 | 설비 로그 1000건 조회 시 3초 이내 응답 |
